O que é um banco de dados

Um banco de dados é um sistema feito para armazenar, administrar e recuperar dados. Ele é a fundação de praticamente todo software moderno: o seu app pode trocar de framework, mas os dados ficam.

Por que não guardar tudo na memória?

A memória RAM é muito rápida, mas é volátil. Se o servidor reinicia, trava ou cai, tudo que estava ali se perde. Além disso, a memória de uma máquina é limitada e não é compartilhada entre vários servidores.

E gravar em arquivo?

Funciona para coisas pequenas, mas logo aparecem os problemas: como achar um registro sem ler o arquivo inteiro? O que acontece se dois processos escrevem ao mesmo tempo? E se a luz cair no meio da gravação? Você acabaria reinventando um banco de dados, só que pior.

RequisitoO que significa na prática
EficienteEncontra e atualiza dados rápido, mesmo com milhões de registros (índices, planos de consulta, cache).
RobustoNão perde nem corrompe dados quando algo falha (log de escrita, transações, backups, réplicas).
EscalávelContinua respondendo quando o volume de dados e de acessos cresce.

SQL e o modelo relacional

Nos bancos relacionais (PostgreSQL, MySQL, SQL Server, Oracle), os dados vivem em tabelas com linhas e colunas, e as tabelas se relacionam entre si por chaves. A linguagem usada para consultar e alterar esses dados é o SQL.

  • Chave primária: identifica cada linha de forma única (o id).
  • Chave estrangeira: aponta para a linha de outra tabela. Um produto pertence a um fabricante através de fabricante_id.
  • Schema-on-write: a estrutura é definida antes. O banco recusa um dado que não segue o schema no momento da gravação.
CREATE TABLE fabricante (
  id    SERIAL PRIMARY KEY,
  nome  TEXT NOT NULL
);

CREATE TABLE produto (
  id             SERIAL PRIMARY KEY,
  nome           TEXT NOT NULL,
  fabricante_id  INT REFERENCES fabricante(id)  -- chave estrangeira
);

-- juntar as duas tabelas numa consulta
SELECT p.nome, f.nome AS fabricante
FROM produto p JOIN fabricante f ON f.id = p.fabricante_id;

ACID

ACID é o conjunto de garantias que faz um banco relacional ser confiável para dinheiro. O exemplo clássico é uma transferência de R$ 100 entre duas contas.

sua contaR$ 1.000
−100 → +100
outra contaR$ 500
AAtomicidade

Tudo ou nada. Se der erro entre o débito e o crédito, nada acontece: as duas contas voltam ao valor original.

CConsistência

A transação leva o banco de um estado válido para outro estado válido, respeitando chaves estrangeiras, restrições e triggers.

IIsolamento

Duas transações rodando ao mesmo tempo não interferem uma na outra. O resultado é como se tivessem rodado em sequência.

DDurabilidade

Depois do commit, o dado está salvo. Crash, queda de energia ou reinício não apagam o que foi confirmado.

BEGIN;
UPDATE conta SET saldo = saldo - 100 WHERE id = 1;
UPDATE conta SET saldo = saldo + 100 WHERE id = 2;
COMMIT;   -- se algo falhar antes daqui: ROLLBACK, e nada muda
Sem transaçãoO servidor cai depois do primeiro UPDATE. Sua conta fica com R$ 900, a outra continua com R$ 500, e R$ 100 somem.
Com ACIDO banco desfaz o débito ao reiniciar. As contas voltam para R$ 1.000 e R$ 500, e você pode tentar de novo.

Isolamento tem níveis

Na prática, bancos oferecem níveis de isolamento, porque isolar totalmente custa desempenho. Vale saber que eles existem e o que cada um evita:

NívelEvitaAinda pode acontecer
Read committedLer dado que ainda não foi confirmadoLer o mesmo registro duas vezes e ver valores diferentes
Repeatable readO caso acimaLinhas novas aparecerem numa segunda consulta (phantom read), dependendo do banco
SerializableTodas as anomalias de concorrênciaMais conflitos e transações abortadas, que precisam ser repetidas

Por tudo isso, SQL é a escolha natural para sistemas financeiros, marketplaces, CRMs e ERPs: lugares onde consistência importa muito.

NoSQL

NoSQL não é uma versão piorada do SQL. É uma família de bancos feitos para casos específicos, com duas características que se destacam:

  • Schema flexível (schema-on-read): você não precisa definir a estrutura antes de gravar. Dois documentos da mesma coleção podem ter campos diferentes.
  • Throughput alto: throughput é quanto trabalho o sistema processa por segundo. Muitos bancos NoSQL foram desenhados para escalar horizontalmente (mais máquinas) e aguentar um volume enorme de leituras e escritas sob carga pesada.
{ "nome": "Ana", "saldo": 1000 }
{ "nome": "Bia", "pix": "bia@email", "tags": ["vip"] }   // mesma coleção, campos diferentes

Impedance mismatch

Esse conceito explica muito por que o NoSQL existe. No seu código, um pedido é um objeto: tem id, itens, dados do cliente e pagamento. No banco relacional, esse mesmo pedido é quebrado em várias tabelas.

pedido = {
  id: 42,
  itens: [...],
  cliente: {...},
  pagamento: {...}
}
⇄
pedidos
clientes
itens
cartoes

Toda vez que você lê ou grava, a aplicação tem que desmontar o objeto em linhas ou remontar as linhas em objeto. Esse descompasso entre o formato do código e o formato do banco tem nome: impedance mismatch.

Bancos de documentos reduzem esse atrito porque guardam o pedido inteiro como um documento só. Nos relacionais, ORMs (Prisma, Hibernate, SQLAlchemy, Entity Framework) fazem essa tradução por você, mas o custo continua existindo: consultas com muitos JOINs, o problema do N+1 e modelos de objeto que não batem com as tabelas.

BASE

Muitos bancos NoSQL rodam em sistemas distribuídos e, por isso, costumam seguir outro modelo de garantias: o BASE.

BABasically Available

Todo request recebe uma resposta, mesmo que o dado não esteja 100% atualizado.

SSoft State

O estado pode mudar mesmo sem input novo. Os dados podem ficar inconsistentes por um tempo.

EEventual Consistency

A consistência se propaga de forma assíncrona. Em algum momento, todas as cópias ficam iguais.

ACIDBASE
PrioridadeEstar sempre corretoEstar sempre no ar
ConsistênciaImediata, após o commitEventual
Escala típicaVertical primeiro (máquina maior)Horizontal (mais máquinas)
Exemplo de usoSaldo bancário, estoque, pedidosLikes, feed, contadores, logs

Ou seja: o modelo BASE prefere ficar no ar a estar sempre consistente.

Teorema CAP

É a pergunta de banco de dados que mais cai em entrevistas. Imagine um banco com dois servidores, os dois com saldo de mil reais.

servidor 1R$ 1.000
— rede —
servidor 2R$ 1.000
CConsistência

Você saca R$ 100 num servidor, e quem consulta o outro já vê R$ 900. Toda leitura reflete o dado mais atual.

ADisponibilidade

Se um servidor cai, o outro continua respondendo. Todo request recebe resposta.

PTolerância a partição

Se os dois perdem a conexão entre si, o sistema continua funcionando.

O teorema diz que você nunca consegue garantir os três ao mesmo tempo. Num sistema distribuído, a rede vai falhar em algum momento, então P é obrigatório. CA, no mundo real, é quase impossível. Sobra escolher entre CP e AP para o momento em que a rede falha:

CP · consistênciaEnquanto os servidores não se falam, o saque é negado. Você sacrifica disponibilidade para nunca mostrar saldo errado.
AP · disponibilidadeAlguém dá um like: um servidor mostra 1.001 e o outro ainda mostra 1.000. Tudo bem, daqui a pouco eles se acertam.

Indo além: PACELC

CAP só fala do que acontece durante uma partição. O PACELC completa a ideia: se há partição (P), escolha entre A e C; senão (E, de "else"), escolha entre latência (L) e consistência (C). Mesmo com a rede saudável, esperar todas as réplicas confirmarem deixa cada escrita mais lenta.

Teste rápido: CP ou AP?

Saldo da conta corrente num app de banco

Mostrar saldo errado pode permitir gastar dinheiro que não existe. Melhor negar a operação por alguns segundos.

Contador de visualizações de um vídeo

Se um servidor mostrar 10.482 e outro 10.479 por um instante, ninguém se prejudica. Ficar fora do ar seria pior.

Reserva do último assento de um voo

Duas pessoas não podem ficar com o mesmo assento. A reserva precisa de uma única verdade.

Feed de posts de uma rede social

Um post chegar alguns segundos depois para parte das pessoas é aceitável. O feed não pode parar.

E a IA nisso tudo?

A IA pode escrever a query, mas saber que um pagamento precisa de consistência e um like não precisa, isso é com você.

Quando você pede para uma IA montar um sistema e não entende de banco de dados, aceita qualquer coisa que ela sugerir. Antes de aceitar um schema ou uma escolha de banco gerada por IA, faça estas perguntas:

  • Esses dados envolvem dinheiro, estoque ou qualquer coisa que não pode ficar errada nem por um segundo? Então preciso de transações ACID.
  • O que acontece com uma operação se o servidor cair no meio dela?
  • Meu modelo de dados é muito relacional (muitos JOINs) ou é um agregado que sempre leio inteiro?
  • Qual o volume esperado de leituras e escritas por segundo? Um único banco relacional bem indexado já aguenta?
  • Se a rede entre réplicas falhar, prefiro negar a operação (CP) ou responder com um dado possivelmente desatualizado (AP)?
  • As consultas que vou fazer têm índice? Peça para a IA explicar o plano de execução (EXPLAIN).
09extra

Perguntas de entrevista

O que é uma transação e por que ela importa?

É um grupo de operações que o banco trata como uma unidade: ou todas são aplicadas, ou nenhuma. Importa porque protege o sistema de estados intermediários, como dinheiro debitado de uma conta e nunca creditado na outra.

Explique as quatro letras do ACID com um exemplo.

Use a transferência de R$ 100: atomicidade (débito e crédito juntos ou nenhum), consistência (o saldo respeita as regras do banco), isolamento (duas transferências simultâneas não se misturam) e durabilidade (depois do commit, sobrevive a um crash).

Quando você escolheria NoSQL em vez de SQL?

Quando o dado tem formato variável, quando o acesso é sempre pelo agregado inteiro (um documento), quando o volume de leitura e escrita exige escalar horizontalmente, ou em casos específicos como cache (chave-valor), relações profundas (grafo) e busca por similaridade (vetorial). Na dúvida, SQL é o ponto de partida mais seguro.

O que é consistência eventual?

É a garantia de que, se as escritas pararem, todas as réplicas vão convergir para o mesmo valor em algum momento. Durante esse intervalo, leituras em réplicas diferentes podem devolver valores diferentes.

Por que CA não existe na prática num sistema distribuído?

Porque partições de rede acontecem e não dá para evitá-las. Se o sistema não tolera partição, ele simplesmente deixa de funcionar corretamente quando a rede falha. Então P é obrigatório, e a escolha real é entre C e A durante a falha.

O que é impedance mismatch e como lidar com ele?

É o descompasso entre o modelo de objetos do código e o modelo de tabelas do banco relacional. Dá para lidar usando um ORM, desenhando o schema pensando nos padrões de acesso, ou usando um banco de documentos quando o dado é naturalmente um agregado.

Glossário

Schema-on-write
A estrutura é definida antes e validada na gravação (relacional).
Schema-on-read
A estrutura é interpretada na leitura; a gravação aceita formatos variados (NoSQL).
Throughput
Quanto trabalho o sistema processa por segundo.
Commit
Confirmação de uma transação. Depois dele, a mudança é durável.
Rollback
Desfazer uma transação que não terminou.
Réplica
Cópia dos dados em outro servidor, para disponibilidade ou leitura.
Partição de rede
Quando partes do sistema ficam sem conseguir se comunicar.
Embedding
Vetor de números que representa o significado de um texto ou imagem.
