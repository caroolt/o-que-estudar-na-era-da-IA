O que olhar antes de escolher

Antes de abrir a documentação de qualquer banco, responda cinco perguntas sobre o seu sistema. Quase toda escolha ruim de banco vem de pular essa etapa e escolher pela ferramenta da moda.

PerguntaO que observarPuxa pra
1 · Formato dos dadosOs registros têm sempre os mesmos campos e se relacionam (usuário, pedido, item)? Ou cada registro tem uma estrutura diferente?Tabelas → SQL. Estrutura variável → documento.
2 · Padrão de acessoComo você busca: por id, por filtros combinados, por texto livre, por similaridade?id → chave-valor. Filtros e JOINs → SQL. Texto → Elasticsearch. Similaridade → vetorial.
3 · LatênciaQuão rápido a resposta precisa chegar ao cliente? Milissegundos numa tela de checkout, segundos num relatório.Muito baixa → cache em memória (Redis) na frente.
4 · CAPSe a rede cair entre dois servidores, você prefere negar a request ou responder com um dado talvez desatualizado?Negar → CP (dinheiro, estoque). Responder → AP (likes, feed).
5 · Leituras vs escritasQual a proporção? Um blog lê muito e escreve pouco; telemetria e logs escrevem sem parar.Muita leitura → réplicas e cache. Escrita massiva → bancos otimizados pra escrita.

Por que escrita em SQL tende a ser mais lenta

Num banco relacional, cada escrita passa por validação de schema, checagem de chaves estrangeiras, atualização de todos os índices e gravação no log de transações (WAL) antes do commit. É exatamente isso que garante o ACID, mas tem custo. Bancos como Cassandra gravam primeiro num log sequencial e numa estrutura em memória, e organizam o resto depois, por isso aguentam volumes de escrita muito maiores.

Por que SQL é o padrão

Comece com SQL. Um Postgres, por exemplo.

  • A maioria dos negócios cabe em tabelas. Um usuário tem N anúncios, um pedido tem N itens. Relações 1:N e N:N são o caso comum, e é exatamente isso que o modelo relacional resolve.
  • É ACID. Transação tudo ou nada e regras (chave estrangeira, UNIQUE, CHECK) que o banco garante por você.
  • 40 a 50 anos de padrão. Ferramentas de backup, migração, monitoramento, ORMs, hospedagem gerenciada em qualquer nuvem, e gente no mercado que sabe operar.
CREATE TABLE usuario (
  id    BIGSERIAL PRIMARY KEY,
  nome  TEXT NOT NULL
);

CREATE TABLE anuncio (
  id          BIGSERIAL PRIMARY KEY,
  titulo      TEXT NOT NULL,
  preco       NUMERIC(10,2) CHECK (preco >= 0),
  usuario_id  BIGINT NOT NULL REFERENCES usuario(id)  -- 1 usuário : N anúncios
);

-- query "complexa" que o SQL resolve numa linha: quem anuncia mais caro, em média?
SELECT u.nome, AVG(a.preco) AS media
FROM usuario u JOIN anuncio a ON a.usuario_id = u.id
GROUP BY u.nome ORDER BY media DESC LIMIT 10;

SQL brilha quando

  • você precisa de queries complexas (JOIN, agregação, filtros combinados que você ainda nem sabe quais serão);
  • você precisa de consistência forte (dinheiro, estoque, reservas);
  • é a lógica de negócio central do sistema, a parte que não pode errar.

"SQL não escala" é mito

O YouTube roda em MySQL, escalado horizontalmente com o Vitess (que nasceu lá dentro). Instagram, Shopify e GitHub também apoiam o núcleo em bancos relacionais. Escalar SQL dá trabalho, mas é feito todo dia: réplicas de leitura, cache, particionamento e sharding. O ponto é que o esforço aparece cedo e é responsabilidade sua.

Quando ir pra NoSQL

São dois motivos principais.

1 · Impedance mismatch

Quando o dado não se traduz bem pra tabela: cada registro tem campos diferentes, ou o objeto é sempre lido e gravado inteiro. Forçar isso em tabelas gera dezenas de colunas vazias ou JOINs pra remontar o objeto toda vez.

2 · Escala

Escala vertical (scale up)Escala horizontal (scale out)
ComoTroca por uma máquina maior: mais CPU, RAM, disco.Adiciona mais máquinas e divide os dados entre elas.
Típico deSQL tradicional (um primário que recebe as escritas).Muitos NoSQL (Cassandra, DynamoDB, MongoDB com sharding).
VantagemSimples. Nada muda na aplicação.Cresce quase sem teto; uma máquina caindo não derruba tudo.
ProblemaCusto sobe rápido e tem limite físico: existe a maior máquina à venda.Escrever em vários nós mantendo consistência é difícil; você aceita trade-offs de CAP.

Chave-valor: o mais simples e o mais usado

Você só consegue buscar pela chave, mas em troca a leitura é quase instantânea. Uma chave de idempotência, por exemplo, guarda o id de um pagamento já processado para que um clique duplo não cobre duas vezes.

# Redis: cache com expiração e rate limit
SET user:42:premium true EX 300        # expira em 5 min
GET user:42:premium

INCR ratelimit:ip:200.1.2.3            # conta requests
EXPIRE ratelimit:ip:200.1.2.3 60       # janela de 1 minuto

SET pagamento:abc123 processado NX EX 86400  # idempotência: só grava se não existir

Documento: cada registro com os campos que existem

{ "produto": "BOLSA",    "tipo_alca": "couro", "cor": "preto" }
{ "produto": "TENIS",    "material_cadarco": "nylon", "numero": 42 }
{ "produto": "NOTEBOOK", "memoria_ram": "16gb", "cpu": "i7" }

No relacional, isso viraria uma tabela com uma coluna para cada atributo possível de cada produto, quase todas vazias. Vale lembrar que o Postgres tem a coluna JSONB: muitas vezes dá pra guardar só a parte variável como documento e manter o resto relacional, sem trazer outro banco.

Grafo: o tipo mais raro na prática

Brilha em perguntas como "amigos de amigos que curtiram X" ou "essa conta está a dois passos de três contas fraudulentas?". Em SQL isso vira JOINs recursivos que ficam lentos a cada nível.

Colunar: somar abril inteiro

Guardando por coluna, uma consulta como "soma de tudo que foi vendido em abril" lê só a coluna valor (e a de data), em vez de cada linha inteira. Colunas também comprimem muito bem.

Detalhe que vale saber: o Cassandra é tecnicamente um banco wide-column, famoso por aguentar escrita massiva (séries temporais, eventos, analytics em tempo real). Já os colunares de data warehouse, como Redshift, BigQuery e ClickHouse, são os otimizados para agregações gigantes.

Vetorial: a base do RAG

Um modelo transforma texto ou imagem num vetor (embedding). Conteúdos parecidos ficam próximos. No RAG, você busca os trechos mais parecidos com a pergunta e os entrega ao modelo como contexto. Para começar, a extensão pgvector faz isso dentro do próprio Postgres.

O fluxo de decisão

  • Comece com SQL (Postgres) como fonte da verdade.
  • Precisa de mais performance de leitura? Coloque um cache do lado (Redis).
  • Analytics pesado? Colunar (Cassandra, Redshift, BigQuery, ClickHouse).
  • Série temporal (métricas, sensores)? Banco de séries temporais (TimescaleDB, InfluxDB).
  • Busca por texto com relevância e filtros? Elasticsearch / OpenSearch.
  • IA com embeddings? Banco vetorial (Pinecone, ou pgvector pra começar).

SQL e NoSQL juntos

Geralmente não é SQL ou NoSQL. São os dois.

O padrão mais comum do mercado é o cache-aside: a aplicação pergunta primeiro pro Redis; se o dado estiver lá, responde na hora; se não estiver, busca no Postgres (a fonte da verdade) e guarda no cache para a próxima vez.

async function isPremium(userId) {
  const key = `user:${userId}:premium`;
  const cached = await redis.get(key);
  if (cached !== null) return cached === "true";           // cache hit: responde na hora

  const { rows } = await pg.query(                            // cache miss: vai na fonte da verdade
    "SELECT premium FROM usuario WHERE id = $1", [userId]);
  const premium = rows[0]?.premium ?? false;
  await redis.set(key, String(premium), { EX: 300 });     // guarda por 5 min
  return premium;
}

O cuidado é a invalidação: quando o usuário vira premium, apague a chave (DEL user:42:premium) junto da atualização no Postgres, ou ele vai ver o valor antigo até o cache expirar. Empresas 100% SQL ou 100% NoSQL existem, mas são raras.

E a IA nisso tudo?

A IA vai sugerir um banco em dois segundos. Saber se ela está certa ou não, isso é com você.

Quando a IA disser "usa MongoDB, é moderno e escala", devolva as perguntas:

  • Qual é o formato dos meus dados? Eles cabem em tabelas e se relacionam?
  • Como eu vou buscar esses dados? Por id, por filtros, por texto, por similaridade?
  • Qual latência o meu cliente precisa?
  • Se a rede cair, prefiro negar ou mostrar dado desatualizado?
  • Qual a proporção de leituras e escritas, e qual volume real espero no primeiro ano?
  • Por que não Postgres? Peça pra IA justificar o que o Postgres (com JSONB, pgvector, réplicas) não resolveria.

Perguntas de entrevista

Como você escolheria o banco de dados para um sistema novo?

Começaria pelas perguntas: formato dos dados, padrões de acesso, latência, requisitos de consistência (CAP) e proporção de leituras e escritas. Sem um motivo forte, começo com um relacional como Postgres e adiciono bancos especializados (cache, busca, analytics) quando aparecer um problema específico.

Qual a diferença entre escalar vertical e horizontalmente?

Vertical é trocar por uma máquina maior: simples, mas caro e com limite. Horizontal é adicionar máquinas e dividir os dados: cresce muito mais, mas traz complexidade de distribuição e trade-offs de consistência.

SQL escala?

Sim. Réplicas de leitura, cache, particionamento e sharding (ex.: Vitess no YouTube) levam bancos relacionais a escalas enormes. O custo é que a parte difícil, principalmente escrita distribuída, fica por sua conta.

Quando usar um banco de documentos em vez de relacional?

Quando o dado tem estrutura variável, é lido e gravado como um agregado inteiro e quase não tem relações entre documentos. Se só uma parte é variável, uma coluna JSONB no Postgres costuma bastar.

O que é cache-aside e qual o maior risco?

A aplicação consulta o cache primeiro e, no miss, busca no banco e popula o cache. O maior risco é servir dado velho: é preciso definir expiração (TTL) e invalidar a chave quando o dado muda.

Por que bancos colunares são bons para analytics?

Porque agregações leem poucas colunas de muitas linhas. Guardando por coluna, o banco lê só o necessário e comprime muito melhor, já que valores da mesma coluna são parecidos.

Glossário

Padrão de acesso
Como a aplicação lê e grava os dados: por quais campos busca, com que frequência, em que volume.
Latência
Tempo entre fazer a request e receber a resposta.
Throughput
Quanto trabalho o sistema processa por segundo.
Escala vertical
Crescer usando uma máquina maior.
Escala horizontal
Crescer adicionando mais máquinas.
Sharding
Dividir os dados entre vários servidores por uma chave.
Lookup
Busca direta por uma chave.
Feature flag
Chave que liga ou desliga uma funcionalidade sem novo deploy.
Rate limit
Limite de requests por cliente num intervalo de tempo.
Idempotência
Fazer a mesma operação duas vezes tem o mesmo efeito de fazer uma.
Data warehouse
Banco feito para análises sobre grandes volumes históricos.
Embedding
Vetor de números que representa o significado de um texto ou imagem.
RAG
Retrieval-augmented generation: buscar contexto relevante e entregar ao modelo antes de ele responder.
Fonte da verdade
O lugar onde está a versão oficial do dado; os outros são cópias.
Cache-aside
Padrão em que a aplicação consulta o cache e, no miss, o banco.
