Um caixa só

🛒Supermercado lotado com um caixa só. Funcionários respondendo preço (as réplicas) ajudam quem só consulta, mas pagar (escrever) continua naquele caixa.

Por que réplica não resolve escrita

Toda escrita feita no primary precisa ser copiada para todas as réplicas. Com 10 réplicas, um post vira 11 escritas no total. Réplica multiplica a capacidade de leitura, não a de escrita.

Escalar pra cima vs escalar pra fora

  • Vertical (scale up): uma máquina maior. Simples, sem mudar código, mas tem teto e o preço cresce muito mais rápido que o desempenho.
  • Horizontal (scale out): várias máquinas, cada uma com uma parte dos dados. É o que sharding faz.

Partição ou shard?

Muitas vezes partição é a divisão dentro da mesma máquina (como o PARTITION BY do Postgres) e shard é a divisão entre máquinas diferentes. Na prática, quase todo mundo usa como sinônimo.

// a aplicação decide pra qual banco vai cada registro, olhando a chave
const shards = [dbA, dbB, dbC];
function shardFor(postId) {
  return shards[escolher(postId)];   // as próximas seções são sobre como implementar escolher()
}
await shardFor(42).query("INSERT INTO posts (id, texto) VALUES ($1, $2)", [42, "oi"]);

Lembrete do vídeo: sharding é ganho de escala, não necessariamente de performance. Você aguenta muito mais escrita, mas consultas que cruzam shards ficam mais lentas e mais complexas.

Cortar em pé ou deitado

✂️Pensa no banco como uma planilha gigante. Dá pra cortar em pé (colunas) ou deitado (linhas).
VerticalHorizontal (sharding clássico)
Cortacolunas ou tabelaslinhas
Cada parte tempedaços diferentes do mesmo registroas mesmas colunas, registros diferentes
Exemploa coluna foto, pesada, vai pra outro storageusuários 1 a 1000 num banco, 1001 a 2000 em outro
Customontar o registro completo exige buscar em dois lugaresescolher a chave certa e lidar com consultas entre shards
-- vertical: separar por responsabilidade
CREATE TABLE users        (id BIGINT PRIMARY KEY, nome TEXT, email TEXT);
CREATE TABLE users_fotos  (user_id BIGINT PRIMARY KEY, foto_url TEXT);  -- pode morar em outro banco

-- horizontal: mesma tabela, linhas em lugares diferentes
-- shard A: posts 1..1000   shard B: posts 1001..2000   shard C: posts 2001..3000

Nota: no mundo real, arquivos grandes como fotos quase sempre vão pra um object storage (S3, GCS) e o banco guarda só a URL. É o mesmo princípio do corte vertical.

Ideia 1: por faixa (key-range)

function escolherPorFaixa(id) {
  if (id <= 1000) return "A";
  if (id <= 2000) return "B";
  return "C";
}
vantagem

Consulta por intervalo é fácil: os posts de 1500 a 1600 estão todos no banco B.

hotspot

Numa rede social, o que todo mundo lê e curte é o post novo, e o post novo tem sempre o maior ID. Todo o tráfego cai no último banco.

Key-range funciona bem quando a chave não cresce junto com o uso, por exemplo dividir por país ou por letra inicial, e quando consultas por intervalo são importantes. IDs sequenciais e datas são os casos clássicos de hotspot.

045:33

Ideia 2: resto da divisão

🃏Distribuir cartas: uma pra cada jogador, em rodízio. Post novo e post velho se misturam e a carga fica equilibrada.
const escolherPorModulo = (id, N) => id % N;   // 7 % 3 = 1 · 8 % 3 = 2 · 9 % 3 = 0

O problema: crescer

Com 3 bancos, a conta é id % 3. Coloque um quarto banco e a conta vira id % 4. Um registro só fica onde estava se id % 3 == id % 4, o que acontece em apenas 3 de cada 12 números. Com 12 posts, só os posts 1, 2 e 12 ficam no lugar.

Com 1 milhão de registros, cerca de 750 mil mudam de banco. No geral, indo de N pra N+1 bancos, mudam N/(N+1) dos registros. Quanto mais bancos você tem, pior.

🃏 resto da divisão
🕛 hash consistente

Registros que mudam de banco, em 1 milhão, ao adicionar um banco (calculado de verdade pro módulo; o ideal teórico de 1/(N+1) pro hash consistente com os bancos bem espalhados).

Ideia 3: hash consistente (o relógio)

🕛Os bancos ficam em pontos de um relógio. Cada post cai num ponto e anda no sentido horário até o primeiro banco. Banco novo só pega o trecho entre ele e o banco anterior.
// anel com os bancos ordenados pela posição (0..359)
const anel = [{ pos: 0, db: "A" }, { pos: 120, db: "B" }, { pos: 240, db: "C" }];

function escolherNoAnel(chave) {
  const p = hash(chave) % 360;                 // onde o post cai no relógio
  const dono = anel.find(n => n.pos >= p);   // anda no sentido horário
  return (dono ?? anel[0]).db;                // passou do fim? volta pro começo
}

// entra o banco D na posição 300: só as chaves entre 240 e 300 mudam (de A pra D)
anel.push({ pos: 300, db: "D" });
  • Nós virtuais: na prática cada banco aparece em dezenas ou centenas de pontos do anel. Isso espalha melhor a carga e, quando um banco sai, a parte dele se divide entre vários vizinhos.
  • Quem usa: Cassandra, DynamoDB, Riak e caches distribuídos como os clientes de Memcached usam variações dessa ideia.
  • Custo: perde a consulta por intervalo, porque chaves vizinhas caem em pontos espalhados do anel.

Partições lógicas (caixas de mudança)

📦Numa mudança você põe tudo em caixas numeradas e as caixas vão pros armários. Caixa = partição lógica. Armário = banco físico.
const PARTICOES = 20;                     // fixo: muito mais caixas que bancos
const mapa = { A: [1,2,3,4,5,6,7], B: [8,9,10,11,12,13,14], C: [15,16,17,18,19,20] };

const particaoDe = (id) => (hash(id) % PARTICOES) + 1;   // essa conta nunca muda
const bancoDe = (p) => Object.keys(mapa).find(db => mapa[db].includes(p));

// banco novo: move caixas inteiras, sem recalcular nada
mapa.D = [6, 7, 14];  mapa.A = [1,2,3,4,5];  mapa.B = [8,9,10,11,12,13];
  • Banco novo: você só leva algumas caixas fechadas pra ele. As outras nem saem do lugar.
  • Usuário famoso: se o MrBeast está na caixa 15 e sobrecarrega o banco C, você deixa a caixa 15 sozinha no C e move as outras. É uma cirurgia.
  • Estático: o número de caixas é definido desde o começo (o exemplo acima).
  • Dinâmico: a caixa cresce e, quando fica grande demais, se divide em duas. O MongoDB faz isso com os chunks. É flexível, mas difícil: tudo acontece com o banco no ar, recebendo leitura e escrita.

Escolha o número de caixas com folga. Se você começa com 20, nunca vai ter mais de 20 bancos sem mudar a conta de novo. Sistemas reais costumam usar centenas ou milhares de partições.

O que fica junto e o índice global

Regra de ouro: o que é buscado junto mora junto.

Se a chave de particionamento é o user_id, o perfil, os posts, as fotos e as curtidas de um usuário caem no mesmo shard. Abrir o perfil vira uma consulta num banco só. Escolher essa shard key é a decisão mais importante do sharding, porque mudar depois é caro.

Buscar por um campo que não é a chave

Por ID, a conta diz o banco. Por nome, a aplicação não faz ideia e teria que perguntar pra todos (scatter-gather). Com centenas de bancos, isso não escala.

-- fácil: a chave diz o shard
SELECT * FROM users WHERE id = 42;

-- difícil: roda em TODOS os shards
SELECT * FROM users WHERE nome LIKE 'Carolina%';

Índice secundário global

Igual ao índice remissivo no fim de um livro: uma lista separada que diz onde cada nome está. A aplicação pergunta primeiro pro índice e depois vai direto no banco certo.

nomeshardids
Carolina24, 5
Ana18
Maria37
  • O custo: quando a Gabriela cria a conta, ela é salva no shard dela e no índice global. Toda escrita vira duas, e as duas precisam ficar consistentes (o DynamoDB, por exemplo, atualiza o GSI de forma assíncrona: a busca pode demorar um pouco pra enxergar o dado novo).
  • Quando vale: só pra busca muito usada e crítica, como nome numa rede social. Data de atualização do perfil não justifica.

Teste rápido: qual estratégia?

Leitura resolvida com réplicas, mas o primary não aguenta o volume de escritas.

Réplica copia cada escrita pra todo mundo. Só dividir os dados divide as escritas.

Uma coluna pesada e pouco lida deixa a tabela de usuários enorme.

Separar colunas por responsabilidade é o corte vertical.

Shards por faixa de ID: o último banco pega fogo e os outros ficam parados. Como chama isso?

IDs novos concentram o uso no último shard.

1 milhão de registros com id % 3. Você passa pra id % 4. Quantos mudam de banco?

Só ficam os que têm id % 3 == id % 4: 3 de cada 12.

Um usuário famoso sobrecarrega sozinho um dos bancos.

Deixe a partição dele sozinha num banco e mova as outras.

Buscar usuários por nome está consultando todos os shards.

Um índice secundário global diz em qual shard cada nome está.

Perguntas de entrevista

Quando você faria sharding?

Só quando uma máquina não aguenta mais as escritas ou o volume de dados, depois de esgotar índices, cache, réplicas, arquivamento e uma máquina maior. Sharding traz custo operacional, consultas entre shards e rebalanceamento; é a bazuca, não o primeiro passo.

Qual a diferença entre particionamento vertical e horizontal?

Vertical separa colunas ou tabelas por responsabilidade; horizontal separa linhas, com o mesmo schema em todos os shards. Sharding normalmente se refere ao horizontal.

Key-range ou hash: quando usar cada um?

Key-range quando consultas por intervalo importam e a chave não concentra o uso (evite IDs sequenciais e datas). Hash quando você quer distribuição uniforme e acessa por chave exata; o preço é perder as consultas por intervalo.

Por que id % N é ruim pra crescer?

Porque mudar N muda o resto de quase todo mundo. De N pra N+1 bancos, N/(N+1) dos registros mudam de lugar: de 3 pra 4, 75%.

Como o hash consistente reduz o rebalanceamento?

Chaves e bancos ficam num anel; cada chave pertence ao próximo banco no sentido horário. Um banco novo só pega o trecho entre ele e o anterior, cerca de 1/(N+1) das chaves. Nós virtuais deixam a distribuição mais uniforme.

Como você lidaria com um usuário que gera muito mais tráfego que os outros?

Com partições lógicas: mais partições que bancos, e a partição dele isolada num banco próprio. Pra leitura, cache e réplicas daquele conteúdo também ajudam; em casos extremos, a chave pode ganhar um sufixo pra espalhar os dados dele.

Como buscar por um campo que não é a shard key?

Scatter-gather em todos os shards (simples, mas não escala) ou um índice secundário global, que aponta o shard de cada valor. O índice deixa toda escrita dupla e pode ficar levemente atrasado se for atualizado de forma assíncrona.

Glossário

Partição
Um pedaço dos dados; muitas vezes, uma divisão dentro da mesma máquina.
Shard
Um pedaço dos dados guardado em uma máquina diferente.
Scale up / scale out
Máquina maior / mais máquinas.
Particionamento vertical
Separar colunas ou tabelas em lugares diferentes.
Particionamento horizontal
Separar linhas: mesmas colunas, registros diferentes em cada shard.
Shard key
O campo usado pra decidir em qual shard cada registro fica.
Key-range
Cada faixa de valores da chave vai pra um shard.
Hotspot
Um shard recebendo muito mais tráfego que os outros.
Módulo (id % N)
O resto da divisão pelo número de shards decide o destino.
Hash consistente
Chaves e shards num anel; adicionar um shard move só uma fatia das chaves.
Nó virtual
Cada shard aparece em vários pontos do anel pra espalhar melhor a carga.
Partição lógica
Unidade de distribuição menor que o banco; vários ficam em cada banco físico.
Partição dinâmica
Partição que se divide em duas quando cresce demais.
Rebalanceamento
Mover dados entre shards pra equilibrar carga ou adicionar máquinas.
Scatter-gather
Consultar todos os shards e juntar as respostas.
Índice secundário global
Índice de um campo que não é a chave e aponta o shard de cada valor.
