A jornada do app

O vídeo acompanha uma rede social crescendo. Cada solução resolve o gargalo da fase atual, e o próprio crescimento mostra o próximo problema. A ordem importa: cada degrau é mais caro e mais complexo que o anterior, então você só sobe quando o degrau de baixo já não resolve.

  1. Ficou lento? Ninguém sabe ainda por quê.meça
  2. Achou a query? O banco lê a tabela inteira.índice
  3. Leitura repetida? O mesmo post pedido mil vezes.cache
  4. Leitura diferente? Cada usuário pede uma coisa.réplicas
  5. JOIN pesando? Toda leitura junta duas tabelas.denormaliza
  6. Dado velho? Você paga pra guardar o que ninguém lê.arquiva

E quando nem isso basta, porque uma máquina só não aguenta as escritas, aí sim vem o sharding. É o tema do próximo episódio.

01fase 1 · 10 mil usuários0:40

Antes de tudo, meça

Um servidor, um Postgres, e o feed ficou lento. Antes de mudar a arquitetura, descubra qual query está lenta e onde ela gasta tempo. O EXPLAIN mostra o plano que o banco escolheu; o EXPLAIN ANALYZE executa a query de verdade e mostra o tempo real de cada etapa.

EXPLAIN ANALYZE
SELECT * FROM posts WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

-- Seq Scan on posts  (actual time=0.02..4812.3 rows=20 loops=1)
--   Filter: (user_id = 42)
--   Rows Removed by Filter: 9 812 344      <- leu a tabela inteira
-- Execution Time: 4812.6 ms

Como ler o plano

  • Seq Scan: leu a tabela linha por linha. Em tabela grande, quase sempre é o vilão.
  • Index Scan / Index Only Scan: usou um índice. É o que você quer ver numa busca seletiva.
  • Rows Removed by Filter alto: o banco leu muito mais do que devolveu.
  • Para achar as queries lentas de produção, ative a extensão pg_stat_statements e ordene por tempo total.

Quando o problema é a própria query

  • Subquery dentro de subquery: muitas vezes vira um JOIN ou um EXISTS mais simples.
  • JOIN gigante que filtra no final: filtre cedo, para juntar menos linhas.
  • SELECT * trazendo colunas que a tela nem usa.
-- antes: junta tudo e só depois filtra
SELECT p.texto, u.nome
FROM (SELECT * FROM posts) p
JOIN users u ON u.id = p.user_id
WHERE p.created_at > now() - interval '1 day';

-- depois: filtra posts cedo e pega só o que precisa
SELECT p.texto, u.nome
FROM posts p
JOIN users u ON u.id = p.user_id
WHERE p.created_at > now() - interval '1 day';

Nota honesta: o otimizador do Postgres costuma empurrar filtros simples pra dentro sozinho. A regra "filtre cedo" vale mais quando a subquery tem agregação, DISTINCT ou LIMIT, que impedem essa otimização. O EXPLAIN é quem dá a palavra final.

02fase 1 · 10 mil usuários1:23

Índices

Sem índice, o banco varre a tabela toda pra achar os posts de uma pessoa. Com índice, ele vai direto no lugar certo. É a primeira coisa a considerar, antes de qualquer réplica.

-- B-tree (o padrão): igualdade e intervalo, e ainda serve o ORDER BY
CREATE INDEX idx_posts_user_data ON posts (user_id, created_at DESC);

-- hash: só igualdade exata
CREATE INDEX idx_users_email ON users USING hash (email);

-- sem travar a tabela em produção
CREATE INDEX CONCURRENTLY idx_posts_created ON posts (created_at);
TipoBom praExemplo
B-tree (padrão)igualdade, intervalo (BETWEEN, >), ordenaçãoposts criados entre ontem e hoje
Hashsó igualdade exata (=)usuário com email = 'ana@x.com'
Compostofiltros que combinam colunas; a ordem das colunas importa(user_id, created_at)

Índice não é de graça

  • Escrita mais lenta: cada INSERT e UPDATE atualiza o dado e todos os índices da tabela.
  • Mais espaço: o índice é uma estrutura à parte, guardada além do dado.
  • Regra: crie índice nos campos que você busca muito (o WHERE e o ORDER BY das queries quentes). Não em todas as colunas.

Na prática, o B-tree resolve quase tudo, inclusive igualdade. O hash só vale a pena em casos bem específicos.

03fase 2 · 100 mil usuários2:17

Cache

Com 100 mil usuários, cada query é rápida, mas são tantas que o banco chega no limite. E boa parte das leituras é igual: o post que viralizou é pedido milhares de vezes por minuto, e o banco calcula a mesma resposta toda vez.

O cache não deixa o banco mais rápido. Ele tira carga do banco.

async function getPost(id) {
  const key = `post:${id}`;
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);                     // tá lá: devolve na hora

  const { rows } = await pg.query("SELECT * FROM posts WHERE id = $1", [id]);
  await redis.set(key, JSON.stringify(rows[0]), { EX: 60 });  // guarda pra próxima
  return rows[0];
}

Esse é o padrão cache-aside. Os dois cuidados principais são a expiração (TTL) e a invalidação: quando o post é editado, apague a chave junto. Cache dá assunto pra um episódio inteiro.

O limite do cache

Ele só ajuda no que se repete. Com 1 milhão de usuários, cada um abre um perfil diferente, e tudo que não está no cache continua caindo num banco só. Aí entra o próximo degrau.

04fase 3 · 1 milhão de usuários3:13

Réplicas de leitura

Funciona porque uma rede social lê muito mais do que escreve: um post é escrito uma vez e lido por milhares de pessoas. Uma máquina fica só com as escritas (o primary, ou master) e é copiada em várias réplicas que só respondem leitura.

// escrita sempre no primary; leitura numa réplica
const primary  = new Pool({ host: "db-primary" });
const replicas = ["db-r1", "db-r2", "db-r3"].map(h => new Pool({ host: h }));
const reader   = () => replicas[Math.floor(Math.random() * replicas.length)];

await primary.query("INSERT INTO posts (user_id, texto) VALUES ($1, $2)", [42, "oi"]);
const feed = await reader().query("SELECT * FROM posts ORDER BY created_at DESC LIMIT 20");
consistência eventual

A escrita confirma sem esperar as réplicas. Mais rápido, mas a réplica pode mostrar um dado antigo por alguns segundos. Bom pra feed, likes, CRUD comum.

consistência forte

A escrita espera a cópia terminar (replicação síncrona). Mais lento, mas nunca mostra dado velho. Necessário em banco e folha de pagamento.

Failover

Se o primary cair, uma réplica é promovida a novo primary. Ferramentas como Patroni, ou os bancos gerenciados da nuvem (RDS, Cloud SQL), fazem isso automaticamente.

Pegadinha clássica: ler o que acabou de escrever

O usuário publica e recarrega a página, e o post não aparece, porque a leitura caiu numa réplica atrasada. Uma solução comum: por alguns segundos depois de uma escrita, as leituras daquele usuário vão pro primary (read-your-writes).

05fase 3 · 1 milhão de usuários4:26

Normalizar ou denormalizar

Olhando o EXPLAIN de novo: toda leitura de post faz um JOIN com a tabela de usuários só pra pegar o nome do autor.

-- normalizado: cada dado num lugar só
SELECT p.texto, u.nome FROM posts p JOIN users u ON u.id = p.user_id;

-- denormalizado: o nome do autor duplicado no post
ALTER TABLE posts ADD COLUMN nome_autor TEXT;
SELECT texto, nome_autor FROM posts;              -- sem JOIN

-- o preço: o usuário mudou de nome
UPDATE posts SET nome_autor = 'Ana Souza' WHERE user_id = 42;  -- mil linhas

Regra prática: comece normalizado e denormalize só o campo que aparece em toda leitura quente e quase nunca muda. Relações muitos-pra-muitos usam uma tabela intermediária com os dois ids.

06fase 4 · vários servidores5:25

O básico bem feito

Connection pooling

Abrir uma conexão com o Postgres custa caro (cada uma é um processo no servidor). Com vários servidores abrindo uma conexão por request, o banco gasta mais tempo abrindo conexão do que respondendo. Um pool mantém algumas conexões abertas e as reaproveita. No Postgres, o PgBouncer faz isso na frente do banco.

const pool = new Pool({ max: 20 });   // 20 conexões abertas, reaproveitadas
await pool.query("SELECT 1");         // pega uma livre e devolve ao terminar

Paginação

O feed não precisa trazer os mil posts de uma vez, só os 20 que cabem na tela. A paginação por cursor é melhor que OFFSET em tabelas grandes, porque o OFFSET 100000 ainda lê e descarta 100 mil linhas.

-- offset: simples, mas fica lento nas páginas do fundo
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 40;

-- cursor: continua de onde a página anterior parou (usa o índice)
SELECT * FROM posts WHERE created_at < '2026-10-12 18:03'
ORDER BY created_at DESC LIMIT 20;

Materialized view

Uma query cara guardada pré-calculada, como se fosse uma tabela. Ótima pro dashboard de crescimento que o time abre toda hora. Assim como um cache, ela fica desatualizada e precisa ser atualizada de tempos em tempos.

CREATE MATERIALIZED VIEW crescimento_diario AS
SELECT date_trunc('day', created_at) AS dia, count(*) AS novos
FROM users GROUP BY 1;

REFRESH MATERIALIZED VIEW CONCURRENTLY crescimento_diario;  -- num cron, de hora em hora

(O CONCURRENTLY exige um índice único na view.)

07fase 5 · bilhões de posts6:23

Hot e cold storage

Com o tempo, a maior parte do dado vira passado. O Facebook existe há uns 20 anos, e quase ninguém lê post de 2010; o que é lido de verdade é o do último ano. Mesmo assim, você paga máquinas rápidas pra guardar tudo.

hot storage🔥 rápido · carodado recente, muito acessado
arquiva →
cold storage / archive🧊 lento · baratodado antigo, raramente lido
  • Motivo principal: custo. As máquinas quentes ficam leves e a conta da nuvem cai.
  • O preço: buscar um dado arquivado é bem mais lento, e migrações e queries ficam mais complexas.
  • Na prática: particione por data (PARTITION BY RANGE (created_at)) e mova partições antigas pra um storage barato, como S3 com Glacier, ou um data warehouse.

O meme do like que some quando você curte um post antigo e recarrega provavelmente é isso: o post está num armazenamento frio, com menos funcionalidade ao vivo.

CREATE TABLE posts (id BIGINT, texto TEXT, created_at TIMESTAMPTZ)
  PARTITION BY RANGE (created_at);

CREATE TABLE posts_2026 PARTITION OF posts
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

-- partição de 2015 vira arquivo: desanexa, exporta pro storage frio e apaga
ALTER TABLE posts DETACH PARTITION posts_2015;

Perguntas de entrevista

O banco ficou lento. Por onde você começa?

Medindo: descubro as queries mais caras (pg_stat_statements, logs de slow query) e leio o plano com EXPLAIN ANALYZE. Só depois escolho a solução, da mais barata pra mais cara: query e índice, cache, réplicas, modelagem, e só no fim particionamento e sharding.

Qual a diferença entre índice B-tree e hash?

B-tree mantém os valores ordenados, então serve igualdade, intervalo e ordenação. Hash só serve igualdade exata. O B-tree é o padrão e resolve a grande maioria dos casos.

Por que não criar índice em todas as colunas?

Porque cada índice deixa toda escrita mais lenta (o banco atualiza o dado e todos os índices) e ocupa espaço. Índice é pra coluna que aparece em filtros e ordenações das queries quentes.

Quando usar cache e quando usar réplica de leitura?

Cache quando muitas leituras pedem a mesma coisa e um dado um pouco velho é aceitável. Réplica quando o volume de leitura é alto e variado demais pro cache resolver. É comum usar os dois.

O que é replication lag e como ele aparece pro usuário?

É o atraso entre a escrita no primary e a cópia chegar na réplica. O usuário publica, recarrega e não vê o próprio post. Resolve-se lendo do primary logo após escrever (read-your-writes) ou com replicação síncrona quando a consistência é obrigatória.

Quando denormalizar?

Quando um JOIN aparece em toda leitura quente e o campo duplicado quase não muda (ex.: nome do autor no post). O custo é atualizar todas as cópias quando ele muda e o risco de elas divergirem.

Paginação por OFFSET ou por cursor?

OFFSET é simples, mas o banco lê e descarta todas as linhas puladas, então as páginas do fundo ficam lentas. Cursor (WHERE created_at < último visto) usa o índice e mantém a mesma velocidade em qualquer página.
