011:10

Ler é fácil, escrever é difícil

💬Você escreve um comentário uma vez. Cem, mil pessoas leem depois. Pra cada escrita podem existir centenas de leituras.

Leitura não muda o estado do banco: mil leituras simultâneas não brigam entre si, e por isso réplicas escalam leitura tão bem. Escrita muda o dado, precisa ser copiada pra todo lado e, quando duas mexem na mesma linha, uma pode atropelar a outra.

Por isso a estratégia pra escalar leitura (cache, réplicas) é diferente da estratégia pra escalar escrita (sharding, menos disputa pela mesma linha).

022:04

Transação: tudo ou nada

💸Um Pix que sai da sua conta e nunca chega na outra. A transação existe pra isso não acontecer.
Gabriela100 → 0
BEGIN … COMMIT
Carolina0 → 100
BEGIN;
UPDATE contas SET saldo = saldo - 100 WHERE id = 1;  -- Gabriela
UPDATE contas SET saldo = saldo + 100 WHERE id = 2;  -- Carolina
COMMIT;   -- se qualquer passo falhar: ROLLBACK, e nada aconteceu

Esse "tudo ou nada" é o A de ACID, atomicidade (episódio 1). Enquanto a transação roda, o banco trava as linhas que ela alterou; outras escritas nessas linhas esperam o COMMIT ou o ROLLBACK.

Na aplicação (Node + pg), sempre com o mesmo cliente da conexão:

const c = await pool.connect();
try {
  await c.query("BEGIN");
  await c.query("UPDATE contas SET saldo = saldo - $1 WHERE id = $2", [100, 1]);
  await c.query("UPDATE contas SET saldo = saldo + $1 WHERE id = $2", [100, 2]);
  await c.query("COMMIT");
} catch (e) {
  await c.query("ROLLBACK"); throw e;
} finally { c.release(); }

A transação protege contra falha no meio. Sozinha, ela não protege de duas pessoas lendo o mesmo valor ao mesmo tempo.

Race condition

💳Casal com cartão conjunto e R$ 100. No mesmo segundo, um compra um lanche de 10 e o outro um tênis de 50. Os dois leem 100.

// o código "lê, calcula, salva": funciona com 1 pessoa, quebra com 2
const { saldo } = await db.one("SELECT saldo FROM contas WHERE id = $1", [id]);
await db.query("UPDATE contas SET saldo = $1 WHERE id = $2", [saldo - valor, id]);

// correção mais simples quando dá: deixa o banco fazer a conta, de forma atômica
await db.query("UPDATE contas SET saldo = saldo - $1 WHERE id = $2 AND saldo >= $1", [valor, id]);

Isso é double spend (gasto duplo): uma das escritas sumiu. O nome do problema é race condition, porque o resultado depende de quem chega primeiro.

Dica: quando a regra cabe numa única instrução (saldo = saldo - 10), o próprio banco serializa as escritas na linha. Os locks entram quando você precisa ler, decidir no código e só depois escrever.

    Lock pessimista

    🚪O provador de loja: entrou, a plaquinha vira "ocupado" e quem chega depois espera na fila.
    BEGIN;
SELECT saldo FROM contas WHERE id = 1 FOR UPDATE;  -- trava a linha até o COMMIT
-- a aplicação decide com o valor lido...
UPDATE contas SET saldo = saldo - 10 WHERE id = 1;
COMMIT;
    • Quem espera: outra transação que tenta FOR UPDATE ou UPDATE na mesma linha. No Postgres e no MySQL (InnoDB), um SELECT comum continua lendo a versão já confirmada; ele não fica bloqueado.
    • Vantagens: simples, seguro, sem update perdido.
    • Desvantagens: fila e gargalo quando muita gente disputa a mesma linha, e deadlocks são possíveis. Mantenha a transação curta: nada de chamar API externa com a linha travada.
    • Variações úteis: FOR UPDATE NOWAIT (falha na hora em vez de esperar) e FOR UPDATE SKIP LOCKED (pula linhas travadas, ótimo pra filas de jobs).

    🔪Duas pessoas cozinhando, uma faca e uma tábua. Uma pega a faca e espera a tábua; a outra pega a tábua e espera a faca. Ninguém solta, ninguém termina.

const [a, b] = [de, para].sort((x, y) => x - y);
await c.query("SELECT id FROM contas WHERE id IN ($1, $2) ORDER BY id FOR UPDATE", [a, b]);

    Com a mesma ordem, os dois Pix começam pela mesma conta: um espera o outro terminar, em vez de os dois ficarem presos.

    Lock otimista

    📄"Este arquivo foi alterado desde que você abriu." Ninguém te impediu de abrir; o sistema só conferiu a versão na hora de salvar.
    -- os dois leem: saldo = 100, version = 2 (ninguém trava nada)
UPDATE contas SET saldo = 90, version = version + 1
WHERE id = 1 AND version = 2;   -- 1 linha alterada: venceu

UPDATE contas SET saldo = 50, version = version + 1
WHERE id = 1 AND version = 2;   -- 0 linhas: a versão já é 3, lê de novo e refaz
    for (let i = 0; i < 3; i++) {
  const { saldo, version } = await db.one("SELECT saldo, version FROM contas WHERE id = $1", [id]);
  const r = await db.query("UPDATE contas SET saldo = $1, version = version + 1 WHERE id = $2 AND version = $3", [saldo - valor, id, version]);
  if (r.rowCount === 1) return;   // salvou
}
throw new Error("conflito: tente de novo");
    • Vantagens: não bloqueia ninguém, escala muito bem, ótimo com muita leitura e pouca escrita concorrente.
    • Desvantagens: precisa de retry, é mais trabalho de implementar e, com muita disputa, várias tentativas falham e o sistema refaz trabalho.
    • ORMs já trazem isso pronto: @Version no JPA/Hibernate, lock_version no Rails, campo version em muitos outros. Em HTTP, o mesmo padrão aparece com ETag + If-Match.

    Leitura suja

    📝Você copia a resposta da prova do colega, ele apaga e escreve outra. Você ficou com uma resposta que nunca foi entregue.
    -- transação A
UPDATE users SET saldo = 0 WHERE id = 1;   -- ainda sem COMMIT
-- transação B, em READ UNCOMMITTED
SELECT saldo FROM users WHERE id = 1;     -- lê 0 (dirty read)
-- transação A
ROLLBACK;                                   -- aquele 0 nunca existiu
    nível de isolamentoleitura suja?observação
    READ UNCOMMITTEDpode acontecerlê sem esperar; SQL Server e MySQL permitem
    READ COMMITTEDnãopadrão do Postgres; só enxerga o que já teve COMMIT
    REPEATABLE READnãopadrão do MySQL (InnoDB); a mesma consulta repete o resultado
    SERIALIZABLEnãoo mais forte: como se as transações rodassem uma por vez

    Detalhe do Postgres: ele não tem leitura suja de verdade. Se você pedir READ UNCOMMITTED, ele trata como READ COMMITTED. O conceito continua valendo pra entrevista e pra outros bancos.

    Quando aceitar: saldo, nunca. Contador de visualizações de um post, tudo bem mostrar 1.001 em vez de 1.000 por um instante.

    Perguntas de entrevista

    O que é uma race condition? Dê um exemplo.

    Quando o resultado depende da ordem em que operações concorrentes acontecem. Exemplo: duas requisições leem o saldo 100, cada uma calcula e salva o próprio valor, e uma escrita apaga a outra (lost update / double spend).

    Transação resolve race condition?

    Não sozinha. Ela garante atomicidade, mas no nível padrão (READ COMMITTED) duas transações ainda podem ler o mesmo valor antes de escrever. É preciso um UPDATE atômico, um lock (FOR UPDATE), versionamento ou um nível de isolamento mais forte.

    Lock pessimista vs otimista: quando usar cada um?

    Pessimista quando a disputa pela mesma linha é alta ou errar é caro (saldo, estoque). Otimista quando conflito é raro e o volume de leitura é alto (perfil, cadastro), aceitando retries.

    O que é deadlock e como evitar?

    Duas transações, cada uma segurando um recurso que a outra precisa. O banco detecta e aborta uma. Evite travando recursos sempre na mesma ordem, mantendo transações curtas, e trate o erro com retry.

    Como implementar lock otimista sem suporte do ORM?

    Coluna version; o UPDATE inclui WHERE version = :lida e incrementa a versão. Se rowCount for 0, alguém mudou antes: releia e tente de novo, com limite de tentativas.

    Quais são os níveis de isolamento e o que cada um evita?

    READ UNCOMMITTED (permite dirty read), READ COMMITTED (evita dirty read), REPEATABLE READ (evita non-repeatable read), SERIALIZABLE (evita também phantoms e anomalias de escrita). Quanto mais forte, mais bloqueio ou mais transações abortadas.

    A IA gerou "lê o saldo, subtrai, salva". O que você revisaria?

    Que o padrão perde escritas sob concorrência. Trocaria por UPDATE … SET saldo = saldo - x WHERE saldo >= x, ou por uma transação com FOR UPDATE, ou por versionamento, e escreveria um teste com duas requisições simultâneas.

    10extra

    Glossário

    Transação
    Grupo de operações que acontece por inteiro ou não acontece.
    COMMIT / ROLLBACK
    Confirmar a transação / desfazer tudo que ela fez.
    Atomicidade
    O A de ACID: tudo ou nada.
    Race condition
    Resultado depende de quem chega primeiro entre operações concorrentes.
    Lost update / double spend
    Uma escrita sobrescreve a outra e uma alteração some.
    Lock
    Trava que impede outra transação de alterar o dado ao mesmo tempo.
    Lock pessimista
    Trava ao ler (SELECT … FOR UPDATE); quem chega depois espera.
    Lock otimista
    Não trava; confere um número de versão ao salvar e tenta de novo se mudou.
    Deadlock
    Duas transações esperando uma pela outra, para sempre.
    Dirty read
    Ler um dado que ainda não teve COMMIT e pode ser desfeito.
    Nível de isolamento
    Quanto uma transação enxerga do que as outras estão fazendo.
